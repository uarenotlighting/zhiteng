# 知疼小程序前端开发前置规范

> 本文件是本项目的强制前置文档，适用于在本目录及其所有子目录中工作的任何 Agent。
>
> **每次收到新需求后，在分析、设计、选型、修改代码或创建文件之前，必须先完整阅读本文件。**
>
> 当前项目只面向小程序端，当前开发和发布目标为：**微信小程序、抖音小程序**。小红书普通小程序保留为后续兼容方向，当前不开发；小红书“小组件”明确不在范围内。

## 1. 项目与技术基线

- 产品：知疼——疼痛记录与就医沟通工具。
- 框架：UniApp。
- 前端：Vue 3。
- 当前目标平台：微信小程序（`mp-weixin`）、抖音小程序（`mp-toutiao`）。
- 人体模型版本边界：小程序首版只开发和打包与 App 3D 同一 Blender 母版导出的真实人体 2D 图、无损区域掩码和区域映射；小程序 3D 的技术文档与资产方案继续保留供后期开发，但不得进入首版页面、分包或验收范围。
- 后续兼容方向：小红书普通小程序（`mp-xhs`），当前不作为开发、测试和交付阻断项。
- 小红书“小组件”是邀请制、单页、独立原生工程形态，不属于当前产品和技术范围；不得因个人主体暂时无法发布普通小程序而擅自改做小组件。
- 主 UI 组件库：**TDesign Uniapp**，使用 UniApp 版本，不使用只面向微信的 `tdesign-miniprogram` 版本。
- 产品不是医疗诊断工具，不得通过界面、文案或交互暗示已经诊断病因或给出具体药物建议。

### 1.1 工程形态与构建边界

本项目是 **HBuilderX 创建和管理的 UniApp Vue 3 项目**，不是 UniApp CLI、Vue CLI 或 Vite 项目。以下规则是强制要求：

- 项目源码保持 HBuilderX 标准根目录结构：`App.vue`、`main.js`、`manifest.json`、`pages.json`、`uni.scss`、`pages/`、`components/`、`static/`、`uni_modules/`。
- 不另建 CLI 形态的 `src/`，不同时维护两套入口、路由或配置。
- 运行使用 HBuilderX“运行 → 运行到小程序模拟器”；发行使用 HBuilderX“发行 → 小程序”。
- 由 HBuilderX 负责 Vue、UniApp、SCSS、平台转译、编译、分包和产物生成，不在项目中重复安装这些构建能力。
- 禁止为了运行微信或抖音而添加 `dev:mp-*`、`build:mp-*` 脚本、Vite 配置、UniApp CLI 包、Vue 构建依赖、Less 编译依赖或平台独立构建工程。
- 项目样式统一使用 UniApp/HBuilderX 支持的 SCSS 和 `uni.scss`；不为了组件库再引入 Less 工具链。第三方库若同时提供已编译 CSS，必须优先使用 CSS 产物。
- 微信、抖音的 AppID 等必要平台信息统一写入 `manifest.json` 对应节点；页面、TabBar 和分包统一写入 `pages.json`。
- 不在源码中手写或维护 HBuilderX 产物里的 `app.json`、`project.config.json`、`project.private.config.json`、`ext.json` 等平台文件，除非 UniApp 官方文档明确要求且业务确实需要。
- `unpackage/` 是 HBuilderX 自动生成的运行/发行产物，不在其中直接改代码，不将其当作源码，不提交到版本库。
- 微信和抖音开发者工具用于运行 HBuilderX 生成的平台产物、真机调试、预览和上传；不在开发者工具中反向维护生成代码，不再执行原生小程序的“构建 npm”作为本项目的日常流程。

开始实现具体产品需求前，还应按需阅读以下现有产品文档：

## 2. 每个需求的强制执行顺序

收到任何前端需求后，必须按以下顺序处理：

1. 完整阅读本文件。
2. 阅读与本次需求直接相关的产品、交互、视觉或数据文档。
3. 默认同时兼容微信和抖音小程序，并避免阻断未来的小红书普通小程序适配；小红书不是当前测试和交付范围。小红书“小组件”不在兼容范围内。
4. 先检查 TDesign Uniapp 是否已有语义和交互接近的组件。
5. 如果 TDesign Uniapp 没有合适组件，再通过网络检索成熟的现成方案。
6. 只有在 TDesign Uniapp 和成熟第三方方案都不能满足需求时，才允许手写组件。
7. 实现后必须完成微信和抖音两端兼容性检查，不能只在微信开发者工具中验证。

不得跳过“组件库检索”和“成熟方案检索”，直接从零手写常见 UI 组件。

## 3. UI 方案选择优先级

必须遵循下面的决策顺序：

```text
TDesign Uniapp 有完全匹配组件
        ↓ 使用原组件
TDesign Uniapp 组件与需求差异不大
        ↓ 通过属性、插槽、Design Token、CSS Variables 或外层样式适配
TDesign Uniapp 完全不适合
        ↓ 搜索经过验证的成熟第三方组件
存在满足微信、抖音兼容要求的成熟组件
        ↓ 引入或参考该组件
没有合格的成熟组件
        ↓ 最后才手写业务组件
```

### 3.1 优先使用 TDesign Uniapp

以下常规能力优先从 TDesign Uniapp 选择：

- Button、Icon、Badge、Tag。
- Navbar、TabBar、Tabs、SideBar。
- Cell、Collapse、Divider、Grid。
- Form、Input、Textarea、Radio、Checkbox、Switch、Stepper。
- Popup、Dialog、Toast、Message、ActionSheet、Drawer。
- Picker、DateTimePicker、Calendar、Cascader。
- Upload、ImageViewer、Loading、Skeleton、Empty、Progress。
- SwipeCell、DropdownMenu、Search、NoticeBar 等通用交互。

使用前应查看当前安装版本的官方文档、组件属性、插槽、事件、平台说明和已知问题，不得仅凭记忆调用 API。

### 3.2 可以进行的轻量样式调整

当 TDesign 组件与需求差别不大时，优先通过以下方式适配：

1. 官方 Props。
2. 官方 Slot。
3. ConfigProvider。
4. TDesign Design Token 和 CSS Variables。
5. 官方提供的自定义类名或外部样式能力。
6. 在业务包装组件的外层添加少量样式。

允许调整颜色、圆角、字号、间距、边框、阴影和局部布局，但必须保持组件的交互语义、可访问性和微信/抖音行为一致。

禁止：

- 直接修改 `node_modules` 或 `uni_modules/tdesign-uniapp` 内的组件源码。
- 大面积复制 TDesign 源码后改名维护。
- 使用深层选择器强行覆盖组件内部结构。
- 依赖仅在微信端有效的内部类名、WXS 或原生节点结构。
- 为了视觉细节破坏组件的焦点、禁用、加载、触摸反馈或安全区处理。

### 3.3 业务包装层

业务页面不要无约束地直接依赖大量 `t-*` 组件。高频组件应在项目内建立轻量包装层，例如：

```text
components/ui/
├── AppButton.vue
├── AppPopup.vue
├── AppDialog.vue
├── AppPicker.vue
├── AppCalendar.vue
├── AppFormItem.vue
└── AppTabBar.vue
```

包装层只负责：

- 应用统一主题和默认属性。
- 收敛微信和抖音差异，并为未来小红书适配保留边界。
- 提供统一事件类型。
- 隔离未来组件库升级或替换的影响。

不要为了包装而包装。一次性使用、没有业务默认值、没有跨端差异的简单组件可以直接使用 TDesign。

## 4. 搜索成熟“轮子”的规则

当 TDesign Uniapp 无法满足需求时，必须先搜索网络，搜索范围包括：

- 组件或框架的官方网站。
- GitHub 官方仓库。
- DCloud 插件市场。
- npm 官方包页面。
- 维护方的更新日志、Issue 和 Release。
- 可信社区中的长期使用反馈。

技术信息和兼容性可能随版本变化，选型时应检索最新资料，优先引用官方文档、官方仓库和正式发布记录。

### 4.1 合格第三方组件的最低要求

候选组件必须尽可能满足以下条件：

- 明确支持 Vue 3 和 UniApp。
- 至少明确支持微信和抖音小程序，而不是只写“支持小程序”；如果宣称支持小红书，也必须有明确证据。
- 有持续维护的公开仓库和可查看的提交历史。
- 有正式版本、更新日志和清晰的升级方式。
- 有完整文档、示例和可复现的使用方法。
- 有明确的开源许可证，且许可证允许当前项目使用。
- 有真实用户、下载量、Star、Issue 或生产项目反馈等市场验证信号。
- 重要 Issue 能得到处理，不存在长期无人维护的大量阻断问题。
- 支持按需引入，体积和依赖数量可接受。
- 不要求接入与需求无关的云服务、统计 SDK 或商业后端。

评价成熟度时，不得只看 Star 数；应综合发布时间、最近更新、下载量、Issue 质量、维护者响应、版本稳定性、文档和真实使用反馈。

### 4.2 必须拒绝的候选方案

以下方案不得直接进入项目：

- 作者自用、演示性质、没有外部用户验证的组件。
- 只有代码片段、博客文章或视频，没有正式仓库和版本管理。
- 长期停止维护或依赖明显过时的组件。
- 没有许可证或许可证不适合商业项目。
- 只验证微信端，却宣称“全端兼容”的组件。
- 没有明确验证抖音小程序、只在微信运行过的组件。
- 需要大面积修改源码才能工作的组件。
- 与项目框架版本冲突，或需要降级 Vue、UniApp、构建工具的组件。
- 以远程脚本、未知 CDN 或闭源运行时代码作为核心依赖的组件。

### 4.3 引入前必须记录的判断

决定新增第三方依赖时，需要在任务说明、变更说明或代码评审信息中写明：

- 为什么 TDesign Uniapp 不能满足。
- 对比过哪些候选方案。
- 选择该方案的依据。
- 微信和抖音兼容证据，以及对未来小红书适配的影响。
- 许可证。
- 维护状态和当前版本。
- 包体积与依赖影响。
- 如果组件失效，项目如何降级或替换。

如果无法获得上述信息，不得贸然引入。

### 4.4 依赖引入与 npm 禁限

“先找成熟轮子”不等于“先安装 npm 包”。本项目的实现和依赖优先级为：

```text
UniApp 内置组件/API/能力
        ↓
已经接入的 TDesign UniApp 组件
        ↓
DCloud 插件市场中成熟的 uni_modules 插件
        ↓
小而边界清晰的项目内实现
        ↓
经评估后的 npm 纯 JS 依赖（最后手段）
```

具体规则：

- TDesign UniApp 通过 `uni_modules/tdesign-uniapp` 和 `easycom` 使用，不再从 npm 安装。
- 新增普通 UniApp 插件时，优先使用 HBuilderX 从 DCloud 插件市场导入 `uni_modules`，并通过 HBuilderX 更新/卸载。
- 默认不在项目根目录创建 `package.json`、`package-lock.json` 和 `node_modules/`。
- 禁止为了代码格式化、CSS 预处理、构建、热更新、运行或发行而安装 npm 依赖；这些由 HBuilderX 处理。
- npm 只允许用于“无对应 UniApp 内置能力、无合格 `uni_modules` 方案、自研明显更高风险”的纯 JS 能力；且必须在安装前获得用户明确同意。
- 允许 npm 例外时，候选包不得依赖 DOM、`window`、`document`、Node.js 运行时、原生二进制模块或某个小程序的独占对象；必须分别验证微信和抖音。
- 不得因为库已安装就全量引入。优先单组件、单函数、明确的子路径引入，禁止无意义地引入整套图标、全部语言包、Demo、源码映射、文档或未使用资源。
- 新依赖不能仅以“`node_modules` 目录多大”判断实际上传大小，但也不能因为编译器可能优化而忽略风险。必须以 HBuilderX 生成的微信/抖音发行产物为准，记录引入前后主包、分包和总包体积差值。
- 引入新依赖后，如果编译产物增量明显高于实际使用能力，或无法说明包体内容，必须撤回依赖并改用更轻量方案。

### 4.5 包体积预算与检查

小程序包体积不等于项目源码目录体积，也不等于 `uni_modules` 或 `node_modules` 在磁盘上的体积。上传边界以 HBuilderX 发行后实际生成的平台产物和对应开发者工具的包分析为准。

开发期内部预算（比平台硬上限更保守）：

- 微信和抖音的主包均以 **1.5 MiB 以内**为预警线。
- 单个普通分包以 **1.5 MiB 以内**为预警线。
- 每个新依赖、图表库、海报/长图库、富文本库、图标集或大型资源都必须单独记录编译增量，不等到上线前再统一减包。
- 平台的硬限制可能调整；每次发布前必须复核微信和抖音官方最新限制，不把某个历史数字当作永久配置。

优化顺序：

1. 删除未使用依赖、页面、组件、Demo、多余语言包和未引用静态资源。
2. 改为按需引入，避免从库总入口引入整库；TDesign 组件通过 `easycom` 按实际标签使用。
3. 压缩图片、图标和字体；非首屏必需的大资源改为合规的远程资源，同时考虑隐私、弱网和失败降级。
4. 按业务路由在 `pages.json` 中使用 `subPackages`，将非首屏、非 TabBar 的独立功能放入普通分包；分包内使用的静态资源优先放在该分包内。
5. 主包只保留启动、TabBar、全局基础能力和确实被多分包复用的资源。不要为了“可能会用”将业务库放入全局入口。
6. 开发阶段需要模拟发布体积时，使用 HBuilderX 菜单的“运行时是否压缩代码”或直接执行“发行”；不为此新增 npm 构建脚本。
7. 使用微信/抖音开发者工具的包分析结果定位大文件和重复代码，完成优化后再回到 UniApp 源码修改。

## 5. 手写组件的边界

只有满足以下任一条件时，才允许手写：

- 属于知疼的核心差异化交互，通用 UI 库不可能直接提供。
- 现有组件无法同时满足微信/抖音兼容、性能、隐私或交互要求。
- 成熟第三方方案的体积、许可证、维护状态或依赖风险不可接受。
- 改造第三方组件的成本已经高于实现一个边界清晰的自有组件。

本项目通常需要自研的业务组件包括：

- `PainBodyMap`：同源真实人体 2D 地图、无损区域掩码命中、点选和范围标记；首版不加载 3D 引擎或 GLB。
- `PainLocationMarker`：疼痛位置、深度和不确定状态表达。
- `PainLevelSelector`：五级口语化强度选择。
- `PainTimeline`：单次疼痛事件变化时间线。
- `BodyPartCard`：关注部位快捷卡片。
- `MedicalSummaryPreview`：就医摘要预览。

即使手写业务组件，其外围的按钮、弹窗、选择器、表单、Toast 等仍优先使用 TDesign Uniapp。

手写组件必须：

- API 边界清晰，不把页面状态隐式写进组件。
- 优先使用 UniApp/Vue 跨端能力，不直接调用单个平台对象。
- 处理触摸、滚动冲突、禁用态、空状态和异常状态。
- 支持暗夜模式和大字号。
- 在微信和抖音两个当前目标平台分别验证。

## 6. 配色与视觉规范

现有产品文档已经确定总体视觉方向，所有页面和组件必须遵守：

- 平静、低刺激、可信任。
- 浅色和暗色都使用 Cursor 聊天的中性灰阶。浅色主操作是近黑 `#141414`，暗色主操作是浅灰 `#E8E8E8`；链接使用蓝色。不使用微信绿，也不把左侧列表头像的绿、红当作界面色。
- 疼痛强度和疼痛位置才使用黄、橙、红等警示色。
- 疼痛色不是品牌主色，不应用于普通主按钮、普通导航和无关装饰。
- 身体图是记录页面的主要视觉和操作区域，不应缩成表单中的小图标。
- 默认使用由统一 Blender 母版正交预渲染的中性真实人体，不使用简笔画，也不强化性别特征。
- 暗夜模式应明显降低亮度和对比刺激，但不能损失文字与操作可辨识度。
- 页面使用大按钮、低信息密度、清晰层级，适应用户疼痛发作时的低操作能力。
- 文案使用自然语言，不要求用户理解专业医学术语。

### 6.1 颜色必须语义化

不得在业务页面散落硬编码色值。应建立统一的语义 Token，并让 TDesign Token 与项目 Token 对齐。所有准确色值以 `../01_品牌配色与暗色模式.md` 为唯一来源；核心 Token 如下：

```scss
// 浅色模式
$color-brand-primary: #141414;
$color-brand-primary-pressed: #0a0a0a;
$color-brand-soft: #e8e8e8;
$color-bg-page: #fcfcfc;
$color-bg-surface: #eeeeee;
$color-bg-subtle: #e1e1e1;
$color-text-primary: #141414;
$color-text-secondary: #5e5e5e;
$color-border: #e4e4e4;
$color-on-primary: #ffffff;
$color-link: #1d66c0;

// 暗色模式
$color-dark-brand-primary: #e8e8e8;
$color-dark-brand-primary-pressed: #d0d0d0;

$color-dark-bg-page: #070707;

```

浅色与暗色模式都必须提供对应值。组件中使用语义名称，不使用诸如 `$red1`、`$gray3` 这种缺少业务含义的名称。

项目根目录的 `uni.scss`、`styles/theme.css` 与 TDesign 品牌 Token 都使用这套中性灰阶；业务页面只引用语义 Token，不得再引入微信绿、头像绿红或 TDesign 默认蓝色。人体模型填充、轮廓和关注色不跟这套界面色走。

当前产品采用 5 档固定强度（1、3、5、7、9），但配色文档只定义了 4 个疼痛色阶（轻微、中等、明显、严重）。在产品确认第五档的颜色或映射规则前，不得自行发明疼痛强度与颜色的对应关系；界面必须同时通过数字、文字或形状表达强度，不能只依赖颜色。

### 6.2 TDesign 主题适配原则

- 通过 Design Token、CSS Variables 和 ConfigProvider 统一主题。
- 优先在主题入口定义一次，不在每个页面重复覆盖。
- 同时维护浅色和暗色变量。
- 检查 Popup、Dialog、TabBar、Navbar、Toast 等挂载层级特殊组件是否正确继承主题。
- 自有业务组件应复用同一套项目 Token，与 TDesign 组件保持一致。

## 7. 交互与可用性原则

- 疼痛发作时的快速记录目标是 3–10 秒完成。
- 快速记录只要求最少字段，允许保存后补充。
- 主要按钮应有足够大的触摸区域，不使用密集的小图标作为唯一操作入口。
- 用户不需要知道准确医学部位，允许大概位置、范围、不确定、表面和深处。
- 一次疼痛事件可以包含多个位置。
- 进行中事件的更新只记录变化，不要求重复填写完整表单。
- 表单必须区分“必填才能完成当前动作”和“可稍后补充”。
- 破坏性动作必须有明确确认，尤其是删除全部健康数据。
- 分享就医摘要前必须提供预览和字段选择。当前 V1 决策为私人备注默认包含，但必须突出展示并允许取消；该默认值在上线前需要完成隐私合规复核。
- 不输出自动诊断、病因判断或具体药物推荐。

## 8. 跨端兼容规则

### 8.1 默认兼容基线

任何新页面、组件和依赖默认都要支持：

- 微信小程序。
- 抖音小程序。

“在微信可运行”不代表任务完成。

小红书普通小程序是后续兼容方向，因此不得无必要地把业务层锁死在 `wx.*` 或 `tt.*`；但当前不要为 `mp-xhs` 新建工程、依赖、脚本或发布配置。小红书“小组件”仍明确不在范围内。

### 8.2 开发限制

- 不直接使用 `wx.*`、`tt.*` 或其他平台对象散落在业务页面。
- 平台能力应通过统一适配模块封装，业务代码调用统一接口。
- 条件编译集中在平台适配层，避免整页充满 `#ifdef`。
- 优先使用 UniApp 基础组件和 Vue 组件，不直接引入微信原生组件作为跨端方案。
- 不依赖浏览器 DOM、`window`、`document` 或只在 H5 可用的库。
- 避免依赖复杂 CSS 选择器、深层穿透、仅部分小程序支持的布局和动画能力。
- Canvas、手势、拖拽、滚动、原生输入框和弹层叠加属于高风险区域，必须查阅微信和抖音最新文档并分别测试。
- 自定义导航栏、底部安全区、胶囊按钮避让和键盘顶起行为必须分别验证。

### 8.3 新依赖的两端最小验证页

新增 UI 库或重要第三方组件时，应先建立或使用独立验证页，至少验证：

- 正常、禁用、加载和错误状态。
- 点击、长按、滑动、滚动和键盘交互。
- 弹窗层级与滚动穿透。
- 深色模式。
- 长文本、大字号和空数据。
- iOS 与 Android 真机表现。
- 微信、抖音两个开发者工具或预览环境。

验证通过后才能在主要业务页面大规模使用。

### 8.4 HBuilderX 与平台工具的职责分工

- 日常编码和工程配置只在 UniApp 源码中完成。
- HBuilderX 根据选择的运行目标自动把同一套 Vue/UniApp 源码编译为微信或抖音产物，不建立 `weixin/`、`toutiao/` 两套业务源码。
- 平台差异先用 UniApp 已封装 API 解决；必须使用平台能力时，集中放到适配层，使用 `MP-WEIXIN` / `MP-TOUTIAO` 条件编译，不复制整个页面。
- 微信开发者工具不负责本项目的 npm 管理或源码构建；不对 HBuilderX 产物执行“构建 npm”后再反向复制到源码。
- 抖音开发者工具中仅导入 HBuilderX 输出的合法小程序产物。抖音官方说明部分 JS 和白名单静态资源可能在未被引用时仍进入上传包，因此禁止把 Demo、备份、大图、未使用 JS 或临时文件复制进产物目录。
- 不得修改 `unpackage/dist/dev/mp-weixin`、`unpackage/dist/dev/mp-toutiao`、`unpackage/dist/build/mp-weixin` 或 `unpackage/dist/build/mp-toutiao` 里的文件来“修复”问题；任何修复都必须回到 UniApp 源码。

## 10. 完成标准

一个前端需求只有同时满足以下条件才算完成：

- 已遵循 TDesign → 成熟第三方组件 → 手写的优先级。
- 没有重复制造已有的通用组件。
- 新依赖具有可说明的成熟度、许可证和微信/抖音兼容证据。
- 样式来自统一 Token，没有在页面中无序散落颜色和尺寸。
- 符合平静、低刺激、可信任的产品视觉方向。
- 支持暗夜模式或至少没有阻断暗夜模式的实现方式。
- 微信、抖音两端均完成相应验证。
- 关键交互包含加载、空、错误、禁用和成功状态。
- 没有诊断性、因果性或具体药物推荐文案。
- 代码没有直接修改第三方组件源码。
- 对无法完全统一的平台差异有明确适配或降级方案。
- 工程仍是单一 HBuilderX UniApp 根目录结构，没有为运行/构建新增 CLI、Vite、Less 或平台独立工程。
- 如果引入了新依赖，已记录 HBuilderX 发行产物的主包、分包和总包体积变化。
- 没有直接修改 `unpackage/` 中的生成文件。
