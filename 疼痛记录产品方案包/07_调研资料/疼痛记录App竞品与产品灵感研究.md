# 疼痛记录 App / 小程序公开内容调研

> 平台：抖音、小红书  
> 采集时间：2026-09-21  
> 关键词：疼痛坐标、疼痛记录、疼痛记录 App、疼痛记录小程序、身体疼痛记录、头痛日记 App、偏头痛记录 App、PainGo、痛绪、小憩、摩丘等。

## 一句话结论

这个赛道真正的机会不是再做一个“疼痛备忘录”，而是把一次难以描述的身体感受，快速变成一份可以回看、比较、导出并向医生说明的结构化记录。

最值得做的产品形态是：**低摩擦记录（2D/轻量 3D 身体图）＋时间趋势＋用药/诱因/缓解效果＋医生友好的 PDF**。3D 是传播亮点，但“记录快、能坚持、医生看得懂”才是长期价值。

## 调研口径与样本说明

- 两个平台均逐条快速筛读了至少约 50 个搜索结果卡；核心产品进一步打开正文、视频说明或评论区核验。
- 严格排除了疾病科普、治疗建议、康复训练、纯病友日记、疼痛文学等非 App/小程序内容。
- 同一开发者连续发布的更新、推广和用户反馈帖没有冒充成多个竞品，而是合并为同一产品线分析。
- 平台存在搜索个性化、内容下架和互动数变化。本报告的互动数字只用于判断需求强弱，不作为精确市场规模。
- 搜索结果中真正独立、明确可识别的产品/原型约十余条；其余相关内容多为同一产品的版本更新、推广、测评或需求讨论。

## 西陆1004「疼痛坐标」重点分析

### 产品演进

首个 Demo 的出发点很清楚：偏头痛或体内疼痛很难用语言说明具体位置，因此用 3D 人体模型选择空间坐标，并允许导出记录。随后升级为全身版，加入类似 CAD 的十字准星、性别中性的开源医学人体模型，并通过遮挡关系区分皮肤表面点与体内点。

在抖音公开回复中，作者提到使用 GPT-6 Astra 协同 Blender 完成原型；在小红书回复中又提到完整优化后考虑放到 GitHub。这里能证明 AI 辅助原型的速度，但不能证明产品已经达到医疗级精度。

### 公开反馈透露的真实需求

1. **需求强，但不是只有偏头痛患者。** 评论里出现儿童、老人、语言表达弱者，以及 ASD/ADHD 等难以清晰表述疼痛的人群。
2. **用户想要的是沟通工具。** 高频表达是“终于能说清楚哪里痛”“给医生看”，而不是自我诊断。
3. **3D 同时是优势和摩擦源。** 用户不知道可以双指缩放、不知道如何把选点移到体内，也会质疑自己能否准确知道内部点位。
4. **产品入口影响转化。** 多条评论在问“在哪里用”“链接是不是被吞了”。公开内容获得高关注，但从内容到产品的路径不够顺。
5. **位置标签不能过度专业。** 用户不一定理解放射痛、钝痛等概念。作者也承认首要任务是位置，其他字段应当次要。

### 互动信号

- 小红书首个 Demo 帖采集时约 7,830 赞、3,656 收藏、302 条评论，说明“把体内疼痛可视化”具有很强的内容传播力和收藏意图。
- 全身版约 414 赞、272 收藏、37 条评论。后续帖子互动下降不代表需求消失，更可能说明“概念惊艳”比“版本更新”更容易传播。
- 抖音同一产品也出现明显的求入口、求上线和使用方法反馈。

### 可以超越它的地方

不要只复制一个 3D 选点器。更完整的差异化应该是：**选点/涂抹 → 发生时间与持续时间 → 强度与感受 → 诱因/用药/缓解 → 历史比较 → 医生摘要**。这样才能从一次性玩具变成长期工具。

## 其他产品的重要发现

### PainGo

PainGo 的公开版本已经覆盖疼痛类型、先兆及先兆症状、伴随症状程度、缓解方式效果、用药和药物有效性。路线图包括 PDF、睡眠日记、头痛计时和统计页。

评论里的高价值信号：

- 多位用户连续要求 Android 版，跨平台是明确空缺。
- 用户希望一次导出多条日记，并接受“一次性买断专业版”。
- 有用户要求把头后侧中分线延伸到肩颈，以表达单侧牵连痛，说明身体图必须支持更细的区域边界或自由涂抹。
- 有人此前用备忘录、事线和系统健康 App 分散记录，证明“一处聚合”本身就是价值。

### 痛绪

痛绪的 MVP 思路非常贴近真实发作状态：不舒服时不想看亮屏、不想打字、也很难判断 1—10 级，因此采用暗夜模式、语音转文字＋AI 填表、口语化疼痛等级，并允许补记昨天或前天。

它最值得借鉴的是“在最糟糕状态下也能完成记录”的设计原则，而非 AI 本身。AI 适合做字段抽取和摘要，不适合直接判断病因。

### 小憩

Apple Watch 上一键记录头痛开始与结束时间，解决了“发作时不愿拿手机，结束后又忘记”的核心摩擦。穿戴端不必复制完整 App，只需保留开始、结束、强度变化、吃药四个快捷动作。

### 摩丘 MuChills

摩丘将身体地图从“记录器”升级成“行动闭环”：记录紧张/酸痛部位，推荐少量拉伸动作，展示肌肉知识卡，再用月度徽章鼓励坚持。它证明疼痛/不适产品可以从被动记录扩展到非医疗性质的自我照护，但必须避免把拉伸建议包装成诊断或治疗。

### 身记

身记强调点击身体位置、感受类型、强度、持续时间，以及按日期、部位和类型统计；还提供皮肤、肌肉、骨骼视图、本地存储和导出备份，并明确不做诊断治疗。这个边界清晰、实现可控，非常适合作为第一版参考。

## 用户需求主题归纳

### 1. 记录必须足够快

- 发作时最多接受 3—10 秒的操作。
- 支持“先记一个点，恢复后补全”。
- 支持昨天/前天补记。
- 语音应转成结构化草稿，由用户确认，不能静默生成医疗结论。

### 2. 身体位置既要直观，也要允许不确定

- 2D 正反面图比 3D 更快；3D 更适合内部位置和传播展示。
- 同时支持点、区域涂抹和左右侧。
- 可选表面/肌肉/骨骼/器官层，但默认不要全部展开。
- 增加“只知道大概区域”“向周围扩散”“牵连到别处”等不确定表达。

### 3. 记录的终点是“看出变化”和“说给医生听”

- 日历热力、部位频次、持续时间、强度趋势。
- 诱因与天气、睡眠、月经、饮食、压力的关联只应表述为“同时出现”，避免因果断言。
- 用药时间、剂量与主观有效性。
- 一页式医生摘要和可选的详细 PDF，支持日期范围筛选。

### 4. 跨平台与隐私是实际竞争点

- Android 需求很强，不能长期只做 iOS。
- local-first 比强制登录更适合私密健康数据。
- 云同步、家庭共享和医生分享都应为可选项，并有明确撤销机制。

## 评论区专项研究：哪些需求值得被看见

本节补充阅读了西陆1004 原始 Demo、全身版、PainGo、痛绪、小憩等核心帖中约 50 条可见的主评论、作者回复和展开回复。西陆原始帖共有 302 条评论，但网页端只稳定展示部分高排序评论，因此这里不是“完整抓取 302 条”，而是对可见高互动样本做定性归纳。评论能发现问题，但不是统计抽样；“点赞多”也可能来自 AI 开发者或新奇概念受众，而不等于长期留存。

### P0：多帖反复出现，应直接进入首版

| 用户信号 | 评论证据 | 产品判断 |
|---|---|---|
| 找不到入口、反复追问产品名 | 西陆的抖音与小红书评论连续出现“叫什么”“在哪里用”“没有看到入口”；小憩评论也追问需要下载什么 | 内容到产品的路径必须短；每个平台的名称、头像和搜索关键词统一，并准备清晰的首次使用说明 |
| Android 缺失 | PainGo 评论中多位用户反复要求 Android；痛绪评论也直接问“安卓 App 没有吗” | iOS 与 Android 应同步规划，不能把 Android 无限后置 |
| 需要记录发生时间和持续时间 | 痛绪评论明确提出“记录疼痛发生时间、持续时间” | 这是疼痛日记的最小数据，不应藏在高级模式 |
| 发作时无法完成复杂操作 | 痛绪、小憩的正文与评论共同验证：不想看手机、结束后会忘、需要补记 | 首页必须支持 3 秒记录；Apple Watch 负责开始/结束/吃药等动作 |
| 导出给医生 | 西陆的高互动内容以“给医生看”为核心；PainGo 用户期待批量 PDF | PDF/医生摘要是核心价值，不是装饰性高级功能 |
| 跨设备记录集中到一处 | PainGo 用户表示备忘录、系统健康和其他记录工具太分散 | 所有端使用同一数据模型；用户升级 App 后不能重新录入历史 |

### P1：明显影响体验，应在首版或紧接首版实现

| 用户信号 | 评论证据 | 设计回应 |
|---|---|---|
| 不知道如何缩放/选择体内位置 | 全身版评论出现“不能放大”“点不出来”；作者需要逐条解释双指缩放、移动摇杆 | 首次使用给 5 秒动效；缩放放到可见按钮；内部/表面切换不要只依靠隐藏手势 |
| 表面痛与体内痛混淆 | 抖音评论建议增加特效区分体表与体内 | 使用皮肤半透明、深度环、剖面或“表面/内部”明确开关，并在保存前文字确认 |
| 自己也不知道精确哪里痛 | 抖音用户直接提出“自己都很难知道自己哪里痛” | 支持大概区域、范围涂抹、扩散方向和“不确定”，不能强迫用户给出伪精确坐标 |
| 身体图区域不够细 | PainGo 用户希望头后侧分区延伸到肩颈，以表达单侧牵连痛 | 支持正反面、左右侧、肩颈连续区域与自由涂抹；不要完全依赖预切分区域 |
| 专业疼痛词不易理解 | 西陆评论指出用户分不清放射痛、钝痛 | 术语旁配通俗例句，也允许“不知道是什么感觉”；高级术语放在展开层 |
| 需要一次性买断 | PainGo 用户明确希望买断专业版 | App 可采用免费基础版＋买断 Pro＋可选云服务，而不是所有功能强制订阅 |

### P2：人数较少，但可能形成真正差异化

- **儿童、老人和语言表达弱者。** 西陆作者和评论都提到这类人难以描述内部疼痛。可做大图标、照护者代记、指给我看模式。
- **ASD/ADHD 与 learning disability 人群。** 高赞评论认为视觉身体图比语言描述友好。需要更少文字、更稳定的交互和感官友好模式。
- **心理痛感/身心共同记录。** 有用户主动提出心理痛感记录。这是相邻机会，但不建议和身体疼痛首版混在一起；可先加入情绪/压力作为可选上下文。
- **家庭提醒。** 痛绪设想把不同报告给不同的人看，并在不舒服时提醒家人不要打扰。可做成用户主动授权的“照护模式”，不能默认共享。
- **开源和数据可携带。** 西陆评论多次询问 GitHub；这反映的不只是开发者兴趣，也包含对长期可用与数据控制权的期待。即便不开源，也应允许导出用户全部原始数据。
- **牵连痛与多点疼痛。** 用户不一定只有一个点；同一次发作应允许多个位置、主次位置与方向关系。

### 必须保留的反对意见

痛绪评论区有人直接评价“伪需求”“需求幻觉”。这类声音值得保留，因为公开内容的高互动可能只是对 AI 开发过程、3D 新奇感或创作者故事感兴趣。

因此首轮验证不应该只看下载量，而要看：

1. 首次记录后 7 天内是否再次记录。
2. 30 天内是否形成至少 3 条记录。
3. 是否有人主动打开趋势或生成医生摘要。
4. 从小程序迁移到 App 后，次月是否仍然记录。
5. 用户删掉 App 前是否导出数据；这能暴露信任、价格或体验问题。

## 目标产品形态：小程序免费轻量版＋App 全量版

你的方向成立，但“引导到 App”不能变成把小程序故意做残。更稳妥的分层是：**小程序完成一个完整但轻量的记录任务，App 解决长期、复杂、跨设备的管理任务。**

### 已确定的开发与发布顺序

本项目正式采用“小程序优先、App 承接、Watch 最后”的顺序：

```text
1. 微信小程序：首个公开版本，完成完整精简版
              ↓
2. 抖音＋小红书：基于 UniApp 主体代码适配并铺开
              ↓（适配期间并行开发）
3. iOS＋Android App：承接更复杂、长期、跨设备需求
              ↓
4. Apple Watch：作为疼痛发作现场的最低摩擦入口
```

具体执行原则：

1. **先发布微信小程序。** 用完整精简版验证记录闭环、连续使用和医生摘要价值，并在微信生态中积累第一批真实用户。
2. **微信核心流程稳定后，立即适配抖音和小红书。** 使用 UniApp 共用主体代码、数据模型和页面，不等待所有高级功能完成；三个小程序的核心能力保持一致，只分别适配登录、授权、分享、审核和平台入口。
3. **适配抖音、小红书期间并行开发 App。** iOS 与 Android App 使用同一后端、数据模型、身体部位配置和统计口径，确保小程序用户未来能继续使用既有数据。
4. **App 稳定后开发 Apple Watch。** Watch 只承载开始、结束、强度变化、服药和补记提醒，不复制完整手机表单。

这三个小程序的目标不是充当下载页，也不是靠人为限制制造转化。它们应当是能独立长期使用的**完整功能精简版**。App 的吸引力来自 3D、高级趋势、批量报告、跨设备同步、系统健康数据和 Watch 等自然增量。

### 各端角色

| 端 | 主要任务 | 免费能力 | 不放入该端的能力 |
|---|---|---|---|
| 微信小程序 | 熟人传播、就医前临时记录、家人代记 | 2D 正反面点选/涂抹、强度、开始时间、持续状态、备注、近期记录、单次分享摘要 | 重 3D、长期高级统计、复杂用药方案、后台持续能力 |
| 抖音小程序 | 视频内容即时转化、概念体验 | 3 秒快速记录、简单身体图、当次结果卡、基础历史 | 强制下载 App、下载后才能完成的流程、外部付费引导 |
| 小红书小程序/小工具 | 搜索承接、收藏后体验、女性与偏头痛内容场景 | 与抖音版相同，强化低亮模式、头部细分和就医摘要预览 | 复杂跨端同步承诺、未经平台确认的外部交易导流 |
| iOS/Android App | 长期健康记录主阵地 | 完整 2D/3D、无限历史、趋势、诱因、用药、缓解效果、语音、PDF、备份与同步 | 医疗诊断和药物处方 |
| Apple Watch | 发作现场的最低摩擦入口 | 开始/结束、强度变化、吃药、快速标记、提醒 | 复杂表单、完整趋势、3D 操作 |

### 建议的小程序“简单模式”

简单模式不是试用弹窗，而是一条完整路径：

1. 点身体位置或头部区域。
2. 选择 5 级口语化强度。
3. 点“刚开始/已经一会儿/结束了”，系统自动记录时间。
4. 可选一句语音或文字备注。
5. 保存后立即看到当次记录卡，并能查看近期简表。

用户即使永远不下载 App，也能完成上述任务。App 的升级理由应自然出现在用户产生复杂需求时，例如“你已经记录 3 次，可以在 App 查看变化趋势”“需要多条 PDF 或 3D 内部定位时可使用完整 App”，而不是阻断保存。

### App 承接的真正增量

- 轻量 3D 与表面/肌肉/骨骼/器官分层。
- 无限历史、日历热力、趋势与相关因素对照。
- 多位置、牵连痛、范围变化和发作过程时间线。
- 用药库、剂量、提醒与延迟疗效回访。
- 批量医生 PDF、自定义日期和隐私字段。
- 语音结构化、Apple Watch、系统健康数据。
- 加密备份、换机恢复、家庭照护与选择性分享。

### 跨端数据设计

不要为四个平台分别维护四套业务数据。建议使用同一套 `PainEntry` 模型和后端 API，再为微信、抖音、小红书、App、Watch 做不同外壳。

- 未登录用户：端内保存，明确告诉用户卸载/清理后的风险。
- 需要同步时：用户主动创建统一账号并同意健康数据同步；平台身份只作为登录凭证之一。
- 小程序到 App：在平台允许的范围内使用一次性迁移码、账号绑定或用户主动导出/导入，不依赖复制隐私数据到剪贴板。
- 合并规则：相同记录使用全局 UUID；以版本号和更新时间解决冲突，避免一次疼痛被同步成三条。
- Apple Watch：离线也能记录，恢复连接后追加事件，不覆盖手机端已经补充的详情。

### 导流与平台规则风险

这里是方案里最需要提前修正的部分。抖音当前公开运营规范明确禁止第三方引流、诱导下载，以及把流程做到一半后要求下载 App 才能继续；也不允许通过剪贴板等方式诱导跳转。换句话说，**抖音小程序可以是品牌体验端，但不能按传统“下载漏斗”粗暴设计。**

微信的运营规范同样长期限制诱导下载；小红书公开协议明确限制把用户导向站外完成交易。三端的审核细节和可用能力会变化，提交前必须按当期后台规则逐项确认。

更安全的做法：

- 小程序自身功能闭环，不出现“下载后才能保存/查看”的断点。
- 产品名称、图标和品牌保持一致，让有进一步需求的用户能够自然搜索到 App。
- 只在确有功能差异的上下文中客观说明“完整 App 支持 3D、长期趋势和手表”，不使用奖励、倒计时、强弹窗或虚假功能限制。
- 不在小程序内引导站外支付；会员权益、购买恢复和平台支付按各端规则分别处理。
- 上线前分别准备微信、抖音、小红书的审核版文案与页面开关，不能用一套导流页面硬发三端。

## 建议做的同款：产品定义

### 核心定位

**“把说不清的疼痛，变成医生看得懂的时间线。”**

这比“3D 疼痛坐标”更完整，也比“健康日记”更聚焦。

### MVP（第一版：微信小程序完整精简版）

1. 2D 人体正面/背面，支持点选和手指涂抹；头部提供更细分区。
2. 强度使用 5 级口语标签，同时在数据层映射到 0—10。
3. 感受快捷项：痛、酸、麻、刺、灼热、胀、跳痛；可选择“不确定”。
4. 开始时间、持续时间/进行中、可能诱因、备注。
5. 用药与其他缓解方式，以及 30/60/120 分钟后的主观效果。
6. “快速记录”和“稍后补全”两种路径。
7. 日历、趋势、按身体部位统计。
8. 本地保存、JSON/CSV 备份、医生版 PDF。
9. 深色/低亮模式；大字号与儿童/老人简化模式。
10. 明确免责声明和危险信号提示，但不输出诊断。

### 第二阶段

- 轻量 3D 全身模型，支持表面/肌肉/骨骼分层和内部点位。
- Apple Watch / Wear OS 快速开始、结束、吃药、强度变化。
- 语音抽取字段，用户确认后保存。
- 睡眠、天气、月经与压力数据的可解释关联视图。
- 家庭成员档案和选择性分享。
- 非医疗的舒缓行动，如呼吸、休息、拉伸记录与前后对比。

### 暂时不要做

- AI 判断病因或推荐具体药物。
- 一上来就加载完整医学级 3D 模型。
- 强制注册、公开社区和复杂社交。
- 把所有专业疼痛术语一次性塞给用户。
- 仅靠会员墙限制核心记录和导出；这会直接伤害长期数据积累。

## 实现思路

### 推荐技术路线

- App：iOS/Android 可用 Flutter 共用业务层，Apple Watch 使用原生 watchOS 扩展，通过 App/WatchConnectivity 同步事件。
- 小程序：确定使用 UniApp 开发，微信、抖音、小红书共用 TypeScript 业务模型、API SDK、页面和组件；简单模式尽量使用 SVG/Canvas 2D，以减少三平台 WebGL 兼容差异。平台登录、隐私授权、审核开关、文件能力和分享能力仍分别封装在适配层中。
- 后端：统一账号映射、同步、迁移码、模型版本和报告任务；不要把平台用户标识当成跨平台唯一身份。
- 本地数据：SQLite（App）或 IndexedDB/小程序本地存储；账号和云同步后置。
- 2D 身体图：SVG 区域 ID＋自由绘制蒙版。点击区域适合统计，涂抹适合表达边界不确定。
- 3D：Three.js/原生 3D 组件加载低模 GLB/glTF；使用 raycasting 得到 meshId、面片、局部坐标或 UV；记录时保存模型版本，避免换模型后坐标漂移。
- 内外表达：皮肤半透明/剖切模式＋深度遮挡；不要只用一个红点，因为用户很难判断点在表面还是体内。
- 报告：本地生成 PDF；默认只显示用户选定时间范围与字段，敏感备注不自动包含。

### 建议的数据结构

```text
PainEntry
  id, createdAt, startedAt, endedAt, isOngoing
  locations[]
    modelVersion, view(2d/3d), bodyPartId, side
    layer(surface/muscle/bone/organ/unknown)
    pointOrArea, localXYZ/uv/mask
  intensity0to10, intensityLabel
  sensations[]
  aura[], accompanyingSymptoms[]
  suspectedTriggers[]
  medication[] {name, dose, takenAt, effectAfterMinutes, effectScore}
  reliefActions[]
  notes, source(manual/voice/watch), completionState
```

### 3D 模型注意事项

YU(ai) 的公开研究提到 BodyParts3D 4.0 全量模型约 2234 个 mesh、228 万三角形，直接放入小程序过重。更现实的方法是把皮肤、肌肉、骨骼、少量主要器官做成独立低模层级，首屏只加载皮肤与最常用区域。

使用开源人体数据时必须逐项核验代码许可与模型数据许可。其方案中提到代码 MIT、人体数据 CC BY 4.0，后者需要署名；不能因为代码可商用就默认模型也没有署名义务。

## 差异化方向排序

| 优先级 | 方向 | 原因 |
|---|---|---|
| P0 | 3 秒快速记录＋稍后补全 | 直接决定发作时是否真的会用 |
| P0 | 医生版 PDF/时间线 | 把零散记录转成明确价值 |
| P0 | Android＋iOS 同步起步 | 公开评论中 Android 缺口非常明显 |
| P1 | 点选＋涂抹＋不确定位置 | 比单纯 3D 点位更符合真实感受 |
| P1 | 用药/缓解效果闭环 | 比“只记痛了”更能帮助复盘 |
| P1 | 暗夜、语音、穿戴端 | 适配疼痛发作时的低操作能力 |
| P2 | 轻量 3D 分层 | 有传播性，也能表达内部位置，但成本较高 |
| P2 | 儿童/老人/表达障碍模式 | 西陆评论已验证，且有社会价值 |
| P3 | 非医疗舒缓建议 | 可提升留存，但要严控医学边界 |

## 商业化建议

- 免费：核心记录、基础趋势、单次 PDF、数据导出。
- 买断或低价 Pro：高级统计、批量 PDF、多设备同步、自定义身体图、长期备份。
- 可选订阅：家庭共享、加密云空间、穿戴端高级自动化。
- 不建议把历史导出或用户自己的原始数据锁在订阅墙后。

公开反馈中已经出现“希望一次性买断”的直接表达。健康记录属于长期资产，买断＋可选云服务通常比纯订阅更容易建立信任。

## 最终建议

项目已确定按以下顺序落地：

1. **微信小程序首发：** 使用 UniApp 完成可独立长期使用的完整精简版，以 2D 正反面、3 秒快速记录、历史、基础趋势和就医摘要验证需求。
2. **抖音＋小红书适配：** 微信版稳定后复用主体代码，分别完成平台能力和审核适配，在各自生态持续积累原始用户；其目的不是强制导流。
3. **App 并行开发并随后发布：** 在适配两个内容平台小程序的同时开发 iOS＋Android App，承接 3D、高级统计、批量 PDF、语音、用药回访、同步等深度需求。
4. **Apple Watch 最后发布：** App 和账号同步稳定后，提供发作现场的开始、结束、强度变化和服药快捷记录。

这条路线既能先在三大平台提供真正有用的轻量产品、积累真实行为数据，又不会把第一版时间耗在 3D、跨设备和 Watch 上。用户未来选择 App，应当源于更深的长期管理需求，而不是被小程序里的功能断点强迫迁移。
